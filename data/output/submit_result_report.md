### 考察

- CatBoost/LightGBM/XGBoostの3モデルの予測は互いに強く相関しており（同一特徴量セットで学習しているため）、
  この3変数に対して重み（Stackingのロジスティック回帰係数、Optimized Weightedのscipy最適化重み）を
  「OOFのLog Lossを最小化するように」学習させると、有効なOOFサンプル数が限られる中で
  **そのOOF区間固有のノイズに適合してしまい**、時期の異なるPublic（Test期間）には汎化しない。
- 一方、Simple Average（等重み）・Weighted Average（OOFスコアの逆数という固定ヒューリスティック）は
  データから重みを「学習」しないぶん、この種の過学習が起きにくく、結果的にPublicでは最も頑健だった。
- `data_exploration_v2_report.md`で指摘されたTrain/Testの時期差（分布シフト）を踏まえると、
  「OOFで最適化された重み」は「OOF期間に最適な重み」であって「Test期間に最適な重み」とは限らない、という
  一般的なリスクが、今回のデータで明確に裏付けられた形。

### 次のアクション候補（更新）

1. **今後はSimple Average / Weighted Averageを基本の提出候補とする**。Stacking・Optimized Weighted Averageは
   理論上は魅力的だが、本データでは過学習しやすくPublicでは逆効果だったため、採用を見送るか、
   重みを均等重みに向けて縮約する正則化（例: 最適化後の重みと1/3の加重平均を取る）を検討する。
2. Stacking/Optimized Weightedを使い続ける場合、OOFの有効サンプル数を増やす（fold数増加、
   複数時系列ホールドアウトの平均を取る等）ことで重み推定の分散を下げる必要がある。
3. `13_autogluon_prototype.ipynb`のWeighted EnsembleもOOF（時系列ホールドアウト）に基づいて重みを学習する点は
   同じ構造のため、同様の過学習リスクがある可能性を念頭に評価する。

## 9. 考察：なぜこれほど改善したか（仮説、未検証）

1. **検証方法自体の違い**: 12_の6-fold TimeSeriesSplitは学習データが少ない初期foldも含めて平均するため、Testの実態（十分な学習データがある状態での予測）より悲観的なOOFになりやすい。13_は「Trainの80%全部で学習し、直近20%で検証する」という、実際のTrain→Testの関係に近い単一ホールドアウトであり、Publicとの整合性が高かった可能性がある。
2. **特徴量の前処理方法の違い**: 13_はLabelEncoding・多項式・ビン化・複合カテゴリ交互作用を使わず、生カテゴリ列と生の`入社日`（datetime型）をAutoGluonの自動前処理に渡している。特にCatBoostはネイティブなカテゴリ処理に強みがあり、LabelEncoderによる恣意的な序数エンコードより有利に働いた可能性がある。
3. **ハイパーパラメータ**: AutoGluonは多数のデータセットでメタ学習された既定パラメータ（HPOなし）で各モデルを1回学習しており、12_のOptuna探索（OOFに対して探索するため、これも一種の「検証セットへの適合」になりうる）より汎化しやすい設定だった可能性がある。
4. **アンサンブルの中身は実質CatBoost単体**（Weighted Ensemble 0.567022 vs CatBoost単体0.567941、差はわずか0.0009）。12_で懸念した「データから学習した重みの過学習」は、13_では実質的に起きていない（ベースモデルが11種と多様で、貪欲法が自然に単一の強いモデルへ収束したため）。

いずれも仮説であり、原因の切り分けはできていない。

### 教訓: 2-split検証は「分布シフトへの頑健性」までは検証できない

2-split（80/20, 75/25）のstdは「Train内でどこを検証に切り出すか」という**サブサンプリングへの感度**を
測るものであり、Train（2011-2014年入社）とTest（2014-2017年入社）という**本質的に異なる母集団への
汎化**とは別の問題である。埋め込み特徴量（384次元をPCAで15次元に圧縮）は、Train内の異なる分割には
安定して対応できたが、そのPCA成分がTrainのテキスト語彙・言い回しの分布に特化していた可能性があり、
時期の異なるTestへの転移では逆にTF-IDFより弱くなった。**「Train内で安定＝Testに強い」とは限らない**
という新しい教訓が得られた。

### 結論: テキスト特徴量はTF-IDFを継続採用、embeddingは不採用

`13_`の代替として着手したテキスト埋め込み案は、今回の検証で「TF-IDFを上回らない」という結論に至った。

（Public 0.550352）**のままとする。

## 56. 原因の切り分け → 検証設計の欠陥2件を特定（重要）

### 欠陥1: 4つのsplitは独立した検証ではなかった（入れ子構造）

検証セットはすべて「入社日順の後ろから切り出す」設計のため、**小さいsplitの検証セットは
大きいsplitの検証セットの部分集合**になっていた。

| split | 検証n | split_70_30の部分集合か |
|---|---|---|
| split_85_15 | 401 | **Yes** |
| split_80_20 | 535 | **Yes** |
| split_75_25 | 667 | **Yes** |
| split_70_30 | 798 | — |

split_85_15 の401名は、他の3つすべてに含まれている（split_70_30の50%、split_80_20の75%）。
つまり**「4/4 splitで有意」は4回の独立した検定ではなく、実質1回の検定（n=798）を
入れ子の4サイズで報告していただけ**だった。中核の401名で効果が出れば、4つすべてが自動的に有意になる。

証拠の量を4倍に見せかけていたことになる。これは`39_`の設計上の誤りである。

### 欠陥2: 13構成から勝者を選んだのに多重比較を補正していない（勝者の呪い）

`39_` は13構成を同じ検証セットで評価し、最良の1つを選んだ。ペアードブートストラップの信頼区間は
**事前に決めた単一の比較**に対しては正しいが、**13個から最良を選ぶ**場合、選ばれた構成の
検証上の優位は系統的に過大評価される。CI半幅が±0.009〜0.011ある中で13回引けば、
真の効果が0でも -0.011 程度の「当たり」は十分に出うる。

欠陥1と2を合わせると、**Gの検証上の -0.0109 は、真の効果がほぼ0でも説明がつく**。

# 66. 文献由来仮説の検証: 集団の勤続賃金カーブ → **不採用**

**仮説の出所**: 小林徹(2016)の中核機構
（`literature/01_early_turnover_literature_review.md` 第3.3節・仮説A）。
「企業特殊的技能が重要な職場ほど勤続に伴い賃金が上がりやすく、離職率が低い」。
本データは単一企業なので、**職場＝初期職種・初期部署** に置き換えて検証した。

集団ごとに24ヶ月の賃金上昇率の平均を出し、個人に付与して定着率を比較した。

提出したのは `CatBoost_r177_BAG_L2` —— **stack_level = 2 のCatBoost**である。
つまり L1 の各モデル（CatBoost・LightGBM・XGBoost・RandomForest・ExtraTrees・NeuralNetTorch）の
**out-of-fold 予測を追加特徴量として受け取ったCatBoost**であり、
我々が `28_`〜`46_` で作ってきた単層のCatBoostとは構造が違う。

| | 我々の構成（`40_` R6_lean） | 勝った構成（`44_` full441 L2） |
|---|---|---|
| 特徴量 | 113列 | **441列** |
| 学習 | Train全件を1回 | **8-fold bagging** |
| 層 | 単層 | **2層（L1のOOF予測をL2の入力に足す）** |
| シード平均 | 5シード | bagging内の8 fold |

**`12_`・`13_` で失敗した「OOFから重みを学習する」とは別物**である点が重要。
ここで学習しているのは重みではなく、**OOF予測を特徴量に加えた上での木モデルそのもの**であり、
かつ bagging により OOF が正しく作られている。

## 71.2 【重要】441列 vs 113列 の結論が覆った

| モデル | 441列 | 113列 | 差 |
|---|---|---|---|
| 我々のCatBoost（`37_` D3 / `40_` R6_lean） | 0.522659 | 0.521729 | **−0.00093**（113が僅かに良い） |
| **AutoGluon（`44_`）** | **0.517685** | 0.522528 | **+0.00484（441が明確に良い）** |

`40_` で「441→113の削減が効いた」と結論したが、その差 −0.00093 は
5シード平均のシード分散（0.0022）以下で、**もともと「同等」としか言えない数字だった**。
**モデルを強くすると、落とした328列に価値があったことが分かった。**

`42_` で「113列より下は単調に悪化する」と確認していたが、
**上側（441列）はモデル次第で価値がある**というのが正しい理解になる。

# 72. `47_autogluon_fixed`: **私が入れた ray が全モデルを壊した** — 提出しないこと

**結論を先に: `47_` の提出ファイル4本はすべて無効。提出してはいけない。**
`44_` の `AG_full441_best_single.csv`（Public 0.517685）が引き続き最良である。

## 72.1 症状

| run | `44_` のモデル数 | `47_` のモデル数 |
|---|---|---|
| lean113_holdout | 149 | **38** |
| lean113_full | 93 | **38** |
| full441_holdout | 63 | **38** |
| full441_full | 41 | **38** |

実行時間は `44_` の約4時間 → **19分**。速くなったのではなく、**大半のモデルが学習前に落ちていた**。

`47_` が学習できたファミリは **ExtraTrees と RandomForest だけ**で、
CatBoost・LightGBM・XGBoost・NeuralNetTorch は**1つも残っていない**。

| | holdout 最良（生存者535名） |
|---|---|
| `44_` lean113 | **0.501305**（WeightedEnsemble_L3） |
| `47_` lean113 | 0.535162（ExtraTrees_r4_BAG_L2） **+0.033857 悪化** |
| `44_` full441 | **0.505552** |
| `47_` full441 | 0.541285 **+0.035732 悪化** |

## 72.2 原因: `ray` の pyarrow バイナリ非互換（**私のミス**）

```
Warning: Exception caused LightGBMXT_BAG_L1 to fail during training... Skipping this model.
  pyarrow.lib.IpcReadOptions size changed, may indicate binary incompatibility.
  Expected 112 from C header, got 104 from PyObject

Traceback:
  autogluon/core/models/ensemble/fold_fitting_strategy.py:1264, in _prepare_data
    X = self.ray.put(self.X)
```

`47_` では「fold を並列化して時間切れを防ぐ」ために
`!pip install "ray>=2.43.0,<2.57.0"` を追加した。ray 2.56.1 は入ったが、
**その pyarrow が Colab 既存の pyarrow とバイナリ非互換**で、`ray.put()` が例外を出す。

ray があると AutoGluon は `ParallelLocalFoldFittingStrategy` を選ぶため、
**k-fold を実際に切る全モデルが `_prepare_data()` の時点で落ちた**。

生き残った RandomForest / ExtraTrees は `44_` のログにあるとおり
`Fitting 1 model on all data (use_child_oof=True)` —— **fold戦略を通らない唯一の2ファミリ**である。
残ったモデルの顔ぶれがこの2つだけだったことが、原因を特定する決め手になった。

**これは環境の問題ではなく、私が良かれと思って足した依存が壊した。**
`44_` のログにあった `Will use sequential fold fitting strategy because import of ray failed` は
**警告であって不具合ではなかった**。逐次でも動いていたものを、並列化しようとして壊した。

## 72.3 `44_` の3つの問題のうち、どれが本物だったか

| # | 問題 | 実際の影響 | `47_` の対処 |
|---|---|---|---|
| 1 | FASTAI全滅（fastai/fastcore不整合） | 時間の浪費のみ。スコアには無関係 | ✅ `excluded_model_types=["FASTAI"]` は正しい |
| 2 | XGBoost 2種が `SettingWithCopyError` | 私のバグ。候補が2つ減っていた | ✅ `_frame()` の `.copy()` は正しい |
| 3 | 時間切れ | 441列で41モデルしか完走せず | ❌ **rayでの解決が裏目**。DyStack無効化は有効 |

**1と2の修正は正しい。3のうち ray だけが誤りだった。**

## 72.4 対処: `48_` は `47_` から ray を抜くだけ

`ray` を入れなければ AutoGluon は `SequentialLocalFoldFittingStrategy` に戻り、
`44_` と同じ挙動になる。その上で以下は維持する。

- FASTAI 除外（時間を他モデルに回せる）
- `_frame()` の `.copy()`（XGBoost 2種が復活する）
- `dynamic_stacking=False, num_stack_levels=1`（`44_` が「最適=1」と判定済み。900秒を節約）
- `time_limit` を伸ばす

`44_` は上記の時間節約なしで441列41モデルでも勝っている。
節約分を全部 CatBoost 系に回せれば、伸びる余地がある。

## 72.5 教訓

**「速くなった」を良い兆候と受け取らない。**
実行時間が想定より大幅に短いときは、まず**成果物の量（モデル数・行数）を数える**。
今回は4つのrunがすべて `38` という同じ数で止まっており、
時間切れなら run ごとにばらつくはずなので、その時点で異常と分かった。

`45_` のときも「実行が短い」ことを確認し、あのときは正常だった。
**短い実行時間そのものは中立で、確認すべきは常に成果物の中身**である。
